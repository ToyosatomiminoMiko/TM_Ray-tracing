# 架构与数据流

## 分层结构

```text
main.c            命令入口:选课/控制输出模式
  |
  +-- Lessons/    每节课一个目录,只负责"画什么"
  |     registry.c  课程注册表(新增课程只改这里)
  |
  +-- Core/
        math/      vec3/mat4:纯数学函数,带公式注释
        render/    framebuffer:内存帧缓冲;output:PPM/帧流输出
        raytrace/  ray/sphere/triangle/plane:求交纯函数

Docs/             理论 + 方法文档
```

## 核心约定:统一先渲染到内存

旧版本里,终端动画直接读内存缓冲,而光照示例直接用 `fprintf` 写 PPM 文件,
导致"同一份场景"有两种不同的输出路径.

重构后的约定只有一条:

> 课程代码只能往 `framebuffer_t`(内存)里画像素,不允许直接写文件.

数据流:

```text
课程渲染函数 -> 内存帧缓冲 framebuffer_t
                     |
                     +--> output_ppm()  PPM 文件(P3 文本)
                     +--> output_ppm_stream() PPM 帧流(P6 二进制,管道给 ffmpeg)

`output_ansi()` 保留在输出层,仅作终端调试工具,不接入命令行流程.
```

这样做的优点:

1. 场景代码与输出方式解耦,同一帧可以导出为 PPM,或编码成 mp4/gif;
2. 动画课程可以无改动地导出成 PPM 序列,再合成 GIF/视频;
3. 课程代码更短,学习者只关注"往像素里填颜色".

## 纯函数约定

数学模块(向量/矩阵/求交)全部写成纯函数:

- 不修改入参;
- 不使用全局可变状态;
- 同样的输入永远得到同样的输出.

例如 `vec3_add`/`intersect_sphere_fast` 都是纯函数.
输出函数(`output_ansi`/`output_ppm`/`output_ppm_stream`)只读取帧缓冲,不修改它.

## 规范

本教程使用`float`

|函数名|参数/返回值类型|
|:-|:-|
|`powf()`|`float`|
|`pow()`|`double`|
|`powl()`|`long double`|

## 课程接口

每节课只需实现:

```c
int lessonXX_render(framebuffer_t *fb, int frame_index, int frame_count);
```

课程注册表里只声明 `animated`(是否动画):

- `animated = 0`:静态课程,只渲染一帧;
- `animated = 1`:动画课程,main 用全局 `ANIMATION_FRAMES` 作为循环帧数,
  依次调用 `render(fb, 0, ANIMATION_FRAMES)` 到
  `render(fb, ANIMATION_FRAMES-1, ANIMATION_FRAMES)`.

所有动画课程共用同一个全局速度:想调快/调慢所有动画,
只改 `lesson.h` 里的 `ANIMATION_FRAMES`(默认 240 帧,MP4 60fps 下 4 秒一圈).

渲染函数拿到的 `frame_index` 是"这是循环里的第几帧",由课程自己决定这一帧的画面.
循环动画用 `lesson_loop_progress(frame_index, frame_count)` 拿到 0..1 的进度,
例如旋转角度 = 进度 × 360°.这就是帧驱动动画:

- 画面只由帧号决定,和秒/帧率完全无关;
- 播放帧率只属于 `ray.sh` 编码端(MP4 默认 60fps,GIF 锁定 25fps),
  改播放帧率只影响"播多快",不会改变每一帧的画面.
